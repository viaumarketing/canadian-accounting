# UGREEN DXP2800 deployment profile — plan and acceptance

Target: UGREEN NASync DXP2800, Intel N100 (4 cores, x86-64), 8 GB RAM (16 GB max), UGOS Pro, Docker Compose.

## Plan

### Memory budget (8 GB total)
UGOS itself, its apps and the Linux page cache need room, so the whole stack is capped at roughly **3.3 GB** of container limits, leaving more than 4.5 GB for the NAS:

| Service | Limit | How it is held there |
|---|---|---|
| postgres | 1 GB | `shared_buffers=256MB`, `effective_cache_size=1GB`, `work_mem=8MB`, `max_connections=40` |
| redis | 192 MB | `maxmemory 128mb`, `noeviction` (queues must not silently lose jobs) |
| api | 512 MB | `--max-old-space-size=320`, Prisma pool 8 |
| worker | 512 MB | `--max-old-space-size=320`, Prisma pool 4, concurrency 1, pauses itself near its limit |
| web | 256 MB | Next.js standalone, `--max-old-space-size=160` |
| caddy | 128 MB | |
| backup | 256 MB | streams (pg_dump → gzip → openssl), never buffers a whole dump |

### Work
1. **Images:** `linux/amd64`; one production-only `server` image (compiled NestJS, `pnpm deploy --prod`, no dev dependencies) runs api, worker and migrations; `web` is Next.js standalone; `backup` is postgres-client + openssl.
2. **Bounded jobs and backpressure:**
   - worker concurrency from `WORKER_CONCURRENCY` (default 1);
   - bank sync capped per run (cursor saved per page, so the next run continues);
   - Shopify keeps one active job per store (database-enforced);
   - when the platform-wide backlog is above `SYNC_MAX_BACKLOG`, manual sync requests get **503 QUEUE_BUSY** and the scheduler skips that round;
   - the worker pauses taking jobs when its memory passes 85 % of its limit.
3. **Storage:** persistent NAS folders for `postgres`, `redis`, `documents`, `backups`, `caddy`. Bank statement files move from the database to `documents/` (content-addressed, checksum-verified on read). Backups now also archive `documents/`.
4. **Migrations and rollback:** a `SchemaCompat` level in the database. Additive migrations keep it, so the previous version can run on the new schema and rollback is app-only, without data loss. A breaking migration raises it: older images refuse to start with `SCHEMA_TOO_NEW`, and rollback must restore the pre-upgrade backup. `rollback.sh` picks the mode automatically, and CI rejects destructive SQL that doesn't raise the level.
5. **Resource dashboard:** host memory, swap, load, disk free on the NAS volumes, per-service memory against its limit, Postgres size and connections, Redis memory, queue depth, a 24-hour history, and low-memory/low-disk warnings shown in System administration and logged by the worker.
6. **Initial administrator:** in production, `SETUP_TOKEN` is required, so nobody on the LAN can claim the instance first.
7. **CI/CD:** GitHub Actions publishes `server`, `web` and `backup` for `linux/amd64` to GHCR, tagged `X.Y.Z` and `X.Y`, only after tests pass.
8. **Verification:**
   - build the amd64 images (under emulation here);
   - load-test the full stack inside Docker Desktop's 3.8 GB VM, which is a harder limit than the NAS's 8 GB;
   - run the acceptance suites (tenant isolation, Shopify reconciliation, bank reconciliation) against the deployment's own PostgreSQL 17;
   - run the backup-restore drill.

### Acceptance criteria (all must pass before "production-ready")
- Docker deployment: clean install from empty folders is healthy; only Caddy publishes ports.
- Backup restoration: database **and documents** restore and match the source.
- Tenant isolation, Shopify reconciliation, bank reconciliation: the automated suites pass against the deployment's PostgreSQL.
- Load: realistic mixed workload with no container OOM-killed, every service under its limit, p95 latencies recorded.
- Things this machine cannot prove (real N100 CPU, UGOS Docker UI, a live Shopify store, a live bank feed) are listed as **not verified**, and the release is **not** called production-ready until they are checked on the DXP2800.

## Results

Everything below ran on a Mac with Docker Desktop: **linux/amd64 images under emulation**, inside a Linux VM with **3.8 GB of RAM** (less than the NAS's 8 GB), with the stack's own memory limits. It was **not run on a DXP2800**.

### Images (linux/amd64)
| Image | Size | Contents |
|---|---|---|
| `server` | 579 MB (was 1.85 GB for each of api and worker) | compiled NestJS, production dependencies only (`pnpm deploy --prod`), Prisma CLI for migrations; runs api, worker and migrate |
| `web` | 352 MB | Next.js standalone output |
| `backup` | 298 MB | postgres 17 client, openssl, scripts |

### Bugs found by running it like the NAS would (all fixed)
1. **api and worker had no internet access.** The only network they were on was `internal: true`, so Shopify, Shopify OAuth and the bank feed could never be reached in production. They now also join `egress`, which is outbound-only with no ports; Postgres and Redis stay internal-only.
2. **NAS folder ownership.** The app runs as uid 1000 with no capabilities and could not write to folders created in UGOS (EACCES, reproduced with real Linux permissions). The one-shot `prepare` service fixes ownership on every start. The backup now runs as uid 1000, because a capability-less root container cannot read the app's 0600 files (also reproduced).
3. **The migration container crashed:** pnpm's `.bin` shim hard-codes the build path. Prisma is now called directly.
4. **502s on POST under load:** a keep-alive race. Node closed idle connections at 5 s, while Caddy reused them for up to 2 minutes, and Caddy won't retry a POST. Fixed with 65 s keep-alive on api and web and 30 s in Caddy. The second run had zero 502s.
5. **A bank import rolled back after 5.4 s** under load (Prisma's 5 s interactive-transaction limit). The limit is now 30 s; it's still atomic.
6. **Imports got slower as the unmatched backlog grew.** Every import re-scored all unmatched transactions in a CPU-bound loop, stalling the API for everyone. Now only the new transactions are scored, and the loop yields between chunks. The bank import median went from 4.4 s to 0.26 s, and overall throughput more than doubled.

### Load test (`scripts/loadtest.mjs`): 12 concurrent users for 10 minutes, 3 companies with 120,000 posted entries (360,000 lines) of history
Mix: dashboard, P&L / balance sheet / trial balance / GST-HST reports, PDF and XLSX exports, journals, posting journals and invoices, 40-row bank CSV imports (files stored in `documents/`), bank transaction lists, resource dashboard. A full encrypted backup ran mid-test.

| | Run 1 (0.9.0) | Run 3 (0.9.2, after fixes 4–6) |
|---|---|---|
| Requests (10 min) | 3,443 | 5,385 |
| Failures | 8 × 502, 4 × 429 (login rate limit: all virtual users share one IP) | **0** |
| p95, slowest operation | 4.4 s (bank import) | 1.8 s (XLSX export, GST report) |
| p95, posting a journal | 1.5 s | 0.45 s |
| Peak memory, all containers together | 0.86 GiB | **0.81 GiB** |
| OOM kills / restarts | 0 / 0 | 0 / 0 |

Peak per container in run 3, against its limit:

| Service | Peak | Limit |
|---|---|---|
| postgres | 306 MiB | 1 GiB |
| api | 216 MiB | 512 MiB |
| worker | 107 MiB | 512 MiB |
| web | 99 MiB | 256 MiB |
| caddy | 64 MiB | 128 MiB |
| redis | 19 MiB | 192 MiB |
| backup | 19 MiB | 256 MiB |

The limits total about 3.3 GB, and actual use stayed under 1 GB. On an 8 GB DXP2800 that leaves several GB for UGOS and its page cache.

**Not representative:** CPU timings. Emulated amd64 on Apple silicon is neither slower nor faster than an N100 in any predictable way, so the latencies are indicative only. Re-run `scripts/loadtest.mjs` on the NAS.

### Acceptance tests in the deployment environment
The full API suite (166 tests) ran inside a linux/amd64 container on the stack's internal network, against a scratch database on the stack's own PostgreSQL 17.11. **All passed**, including:
- tenant isolation: every company route, every role, super admin with no implicit access;
- Shopify reconciliation: orders, fees, payouts, tie-out, refunds, idempotency, against a fake Shopify;
- bank reconciliation: to the cent, locking, credit cards;
- the ledger, reports, backpressure and the schema guard.

### Backup, restore, upgrade and rollback on the amd64 stack
- Encrypted backup of the database plus a documents archive, taken while under load (23 MB dump).
- `upgrade.sh` 0.9.0 → 0.9.1 → 0.9.2: backup first, migrate, health checks all ok.
- **App-only rollback** (no breaking migration): 0.9.2 → 0.9.1 kept all 365,325 journal lines and 442 statements. Prisma's `migrate deploy` in the older image accepts a database that has a newer migration ("No pending migrations", exit 0).
- **Breaking rollback:** after a simulated level-2 migration, 0.9.2 refused to serve (`SCHEMA_TOO_NEW`). `rollback.sh` chose to restore by itself and brought back the pre-upgrade database (level 1, 365,325 lines, balanced) and the documents, including a file deleted after the upgrade. Post-upgrade changes were discarded, as it warns.
- `restore-docs.sh` on its own put back a deleted statement file.

### Monitoring
`/admin/resources` and the Resources tab show:
- NAS memory, swap, load and free disk;
- api and worker memory against their limits, plus heap (the 320 MB `NODE_OPTIONS` caps are in effect);
- Redis memory, database size and connections;
- 5-minute samples kept for 7 days.

Warnings (low memory, a service near its limit, low disk, Redis filling up) appear on every admin page and in the worker log. The worker's memory guard was forced to trigger: at 57 % of a squeezed limit it logged "pausing new jobs".

## Production-readiness gate

| Required acceptance | Status |
|---|---|
| Docker deployment | **Passed on Docker Desktop (amd64 images)**; not yet on the DXP2800 |
| Backup restoration | **Passed** (scratch DB, live replace, documents, failure modes) |
| Tenant isolation | **Passed** (generated route tests, run against the deployment's PostgreSQL) |
| Shopify reconciliation | **Passed against a faithful fake** of Shopify's API; **not yet against your real store** |
| Bank reconciliation | **Passed** (CSV/OFX and fake Plaid); not yet with your real bank files/feed |

**Verdict: not production-ready yet.** The software passes every acceptance test that can run without your hardware and accounts. Four checks remain:
1. Run the install guide on the DXP2800, and run the load test there.
2. Sync your real Shopify store and compare one payout against Shopify's payout report.
3. Import one real bank statement and reconcile it to the cent.
4. Do a restore test on the NAS.

Then call it production-ready.
